# ADR 0002 — Authentication and authorization

- **Status:** Accepted
- **Date:** 2026-10-18
- **Phase:** 2
- **Supersedes:** none

## Context

The architecture requires: server-issued **short-lived access tokens with refresh-token rotation /
revocation**; every action scoped by **tenant, branch, role and permission** enforced **server-side**
for every endpoint and every referenced object (§9, §10); stronger re-authentication / supervisor
PIN for high-risk actions; device enrollment and revocation; and cached, time-bounded offline
permissions. It names **no auth library**.

## Options considered

1. **Passport strategies** (`passport-local`, `passport-jwt`) — pluggable strategy framework.
2. **`jsonwebtoken` + custom guards.**
3. **`jose` + explicit guard chain + DB-backed refresh-token family.**

## Decision

Use **`jose`** for access tokens (HS256; only our own API verifies them) and a **custom guard
chain** — `AuthGuard` → `TenantScopeGuard` → `PermissionsGuard` → `StepUpGuard` — with **opaque,
hashed, rotating refresh tokens** stored in the database with a token-family id and reuse detection.

Reasons:

- Passport is a strategy registry; this system has one token mechanism plus heavy **custom policy**
  (tenant/branch/permission scoping, device binding, offline permission-version windows, step-up).
  Passport would add indirection without providing the isolation logic the architecture actually
  stresses. Explicit guards are more auditable and easier to test with negative cases (§16).
- `jose` is standards-based, actively maintained, and covers both JWT and the JWS used for license
  packages (ADR 0003) — one vetted crypto dependency instead of two.
- Refresh rotation + reuse detection + revocation is inherently DB logic (hashed token, family id,
  `revoked_at`); no library removes that.
- Hand-rolling crypto is forbidden by §10; `jose` and Node's built-in `crypto.scrypt` (PIN hashing)
  are vetted primitives.

## Consequences

- **Positive:** tenant isolation is explicit and testable; one crypto library; tokens are short-lived.
- **Negative:** we implement guards/policy ourselves (more code than a Passport one-liner).
- **Mitigation:** centralize policy in `AuthModule` services; table-driven permission checks.

## Compliance check

Satisfies §9 (server-side authorization for every object), §10 (short-lived tokens, refresh rotation,
step-up, least privilege). No architectural rule violated.
